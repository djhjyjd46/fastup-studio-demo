# Intelephense помечает функции ядра WordPress как Undefined, хотя стабы лежат в проекте

Симптом: в шаблоне темы все вызовы ядра (`get_option`, `get_header`, `esc_html`,
`add_action`, `wp_json_encode`) подсвечены как `Undefined function ... [P1010]`, при том
что `php-stubs/wordpress-stubs.php` лежит прямо в воркспейсе и должен индексироваться.
Перезапуск языкового сервера ничего не меняет.

## Причина

У intelephense есть параметр `files.maxSize`, значение по умолчанию — **1 000 000 байт**
(`DEFAULT_MAX_FILE_SIZE=1e6` в `lib/intelephense.js`). Файлы больше лимита индексатор
**пропускает молча**: ни ошибки, ни предупреждения в логе — просто в индексе нет символов.

`php-stubs/wordpress-stubs.php` весит около 5 МБ, то есть впятеро больше лимита. Поэтому
он не индексируется никогда, сколько ни перезапускай сервер.

## Как отличить эту причину от «стабы вообще не подключены» за одну проверку

Диагностический признак — **избирательность ошибок**. Если рядом лежит маленький файл
стабов (например, `acf-stubs.php` на пару килобайт), его символы резолвятся нормально:
`get_field` чистый, а всё ядро WordPress красное. Значит, каталог стабов индексируется,
и дело не в путях и не в исключениях, а в размере конкретного файла.

Проверяется запросом символа у языкового сервера, а не глазами по диагностике:

- `workspaceSymbol` по `get_field` → находится в `acf-stubs.php`;
- `workspaceSymbol` по `get_queried_object_id` → `No symbols found`.

Один такой запрос закрывает вопрос точнее, чем чтение конфигов.

## Почему нельзя просто поднять лимит

Языковой сервер поднимается плагином `php-lsp` командой `intelephense --stdio` без
`initializationOptions`, и настройки редактора (`intelephense.files.maxSize`) до него
не доезжают. Менять манифест плагина в кэше маркетплейса бессмысленно — он перезапишется
при обновлении плагина.

## Решение: разрезать файл стабов на части меньше лимита

`scripts/split_php_stubs.php` режет стабы по границам top-level объявлений и раскладывает
их по файлам ~900 КБ, сохраняя неймспейсы:

```bash
php scripts/split_php_stubs.php php-stubs/wordpress-stubs.php
```

Исходник переименовывается в `*.php.bak` (расширение `.bak` не попадает под маску `*.php`,
поэтому индексатор его больше не видит), рядом появляются `wordpress-stubs.part1.php` …
`part6.php`.

Границы ищутся токенайзером PHP (`token_get_all`), а не регуляркой: фигурные скобки
встречаются в докблоках (`{@see ...}`) и в интерполяции строк, и построчный счётчик скобок
на таком файле неизбежно разъедется.

## Проверка результата — обязательная, до перезапуска сервера

1. `php -l` по каждой части (предупреждения `Implicitly marking parameter ... nullable`
   на PHP 8.4+ — это свойство самих апстрим-стабов, а не следствие разрезания;
   они точно так же появляются на исходном файле).
2. Сверить число объявлений до и после — оно должно совпасть точно:

```bash
grep -cE "^\s*(final |abstract |#\[[^]]*\]\s*)*(class|interface|trait|function|enum) " wordpress-stubs.orig.php
cat php-stubs/wordpress-stubs.part*.php | grep -cE "^\s*(final |abstract |#\[[^]]*\]\s*)*(class|interface|trait|function|enum) "
```

3. Убедиться, что максимальная часть меньше 1 000 000 байт.

После этого — перезапуск сервера: индекс строится при старте, новые файлы работающий
процесс сам не подхватывает.

## Что запомнить на будущее

Молчаливый лимит на размер файла — типовое поведение индексаторов, а не особенность
intelephense. Если символы из большого сгенерированного файла (стабы, автозагрузка,
дампы схем) не резолвятся, а из маленького соседнего резолвятся — проверять размер
файла против лимита индексатора раньше, чем пути, исключения и конфигурацию.

## Результат проверки после перезапуска (2026-09-05)

Фикс подтверждён на живом сервере: `workspaceSymbol` по `get_queried_object_id` находит
символ в `wordpress-stubs.part2.php` (метод `WP_Query`) и `part6.php` (функция), hover по
`get_option`, `get_header`, `add_action`, `wp_json_encode`, `esc_html` в
`design/wp-templates/front-page.php` отдаёт полные сигнатуры и docblock из стабов.
`P1010 Undefined` по ядру WP не осталось.

Две вещи, которые стоит знать при повторной проверке:

- **Первый запрос после перезапуска может вернуть пустоту** — индексация ~5 МБ стабов идёт
  несколько секунд, и «No symbols found» в этот момент означает «ещё не дочитал», а не
  «не подхватил». Повторить запрос, прежде чем чинить то, что не сломано.
- **Пустая диагностика ничего не доказывает** — харнесс показывает только новые проблемы.
  Доказательство даёт положительный отклик: `workspaceSymbol` с найденным файлом-частью
  или hover с текстом docblock. Проверять надо именно так.
