# Диагностика: нейросеть показывает не ту страницу сайта

Воспроизводимый порядок разбора для случая, когда ИИ-поисковик (ChatGPT, Яндекс.Нейро,
Google AI, Gemini) отвечает про компанию, опираясь на главную или на случайную статью,
вместо профильной страницы услуги — и делает из-за этого неверный вывод («у них это
дополнительная услуга, а не направление»).

Собран по реальному разбору fastup.by 2026-08-30. Переносится на любой клиентский сайт.
Наши цифры и факты сюда не входят — только порядок действий.

## Зачем отдельная методика

Соблазн решать этот случай «по ощущению» велик, а перебор версий дорог: в исходном разборе
диагноз менялся **четыре раза** за день, и три версии из четырёх оказались неверными.
Порядок ниже отсортирован так, чтобы дешёвые и проверяемые вещи шли раньше дорогих
догадок.

## Шаг 0. Получить дословный транскрипт, а не пересказ

**Не начинать работу с пересказа по памяти.** Просить у клиента (или у себя) точный текст
переписки с ИИ: какой был запрос дословно, что ответила модель, какие URL она назвала.

Причина, а не формальность: в исходном разборе пересказ по памяти («ИИ нашёл главную, там
одна строчка») разошёлся с реальным транскриптом почти полностью — в транскрипте модель
цитировала как раз специализированную страницу, а причиной назвала совсем другое.
Полдня ушло на проверку версии, которой не существовало.

Дополнительно: **самообъяснение модели — не лог ранжирования.** ИИ в чате правдоподобно
рационализирует свой ответ задним числом. Транскрипт нужен как факт «что было сказано», а
не как техническая причина. Причину устанавливают шаги 1–4.

## Шаг 1. Снять технические блокировки (дёшево, проверяется за минуту)

```bash
# canonical: не схлопывается ли страница в другую
curl -sS "<URL>" | grep -oE '<link[^>]*rel="canonical"[^>]*>'

# meta robots: открыта ли к индексации
curl -sS "<URL>" | grep -oiE '<meta[^>]*name="robots"[^>]*>'

# редирект/подмена для ИИ-ботов (проверять каждый UA отдельно)
for UA in \
  "Mozilla/5.0 (compatible; GPTBot/1.1; +https://openai.com/gptbot)" \
  "Mozilla/5.0 (compatible; PerplexityBot/1.0; +https://perplexity.ai/perplexitybot)" \
  "Mozilla/5.0 (compatible; YandexBot/3.0; +http://yandex.com/bots)" \
  "Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/128.0"; do
  curl -sS -A "$UA" -o /dev/null -w "%{http_code} %{url_effective} redirects=%{num_redirects}\n" -L "<URL>"
done
```
Ожидаемая норма: `200`, `canonical` на себя, `index, follow`, ноль редиректов у всех UA.
Расхождение между ботами и браузером — отдельная находка (клоакинг или блокировка).

## Шаг 2. Посмотреть, какую страницу выдаёт поисковый индекс

Это ключевой шаг, и он чаще всего и содержит ответ. ИИ-поисковики опираются на поисковый
индекс: **какая страница ранжируется — ту он и процитирует.**

```bash
# Google Search Console: постранично + по запросам
python scripts/gsc_report.py --dimensions page,query --query-filter "<тема>" --days 90
```
Что искать:
- **Ранжируется ли профильная страница вообще** и на каких позициях.
- **Не забирает ли её запросы другая страница того же сайта** — статья, блог, старый URL.
  Это и есть каннибализация, и она чаще внутренняя, чем «нас нет в выдаче».
- **Участвует ли главная** — часто оказывается, что нет вовсе (0 показов), и версия
  «ИИ берёт главную из выдачи» отпадает.

Ограничения инструментов, которые надо знать заранее и не искать обходной путь:
- **Яндекс.Вебмастер не даёт постраничной разбивки** — только запросы по хосту целиком.
- **Bing/ChatGPT** — API нет; живая выдача проверяется руками, автоматический запрос из
  скриптовой среды часто возвращает капчу или подменённый результат.

## Шаг 3. Проверить старые URL и редиректы

Отдельно ищутся URL, которые **ранжируются, но ведут не туда**: страница переименована,
редирект стоит на другой материал, а поисковик всё ещё держит старый адрес и отдаёт ему
показы по целевым запросам.

```bash
curl -sSI "<старый-URL>" | grep -iE "^HTTP|^location"
grep -n "RewriteRule.*R=301" .htaccess
```

**Прежде чем менять цель редиректа — выяснить, что он склеивает.** В исходном разборе
редирект соединял две статьи между собой (они каннибализировали друг друга), и попытка
перенаправить его на коммерческую страницу сломала бы верное решение. Спрашивать владельца,
а не догадываться по URL.

Если старый URL не нужен: `RewriteRule ^<путь>/?$ - [G]` даёт **410 Gone** — сигнал
«удалено навсегда», который поисковики обрабатывают быстрее, чем 404. Плюс удаление URL
руками в Search Console и Яндекс.Вебмастере.

## Шаг 4. Найти внутреннюю конкуренцию между своими же страницами

Проверить **все** страницы и статьи сайта, которые претендуют на ту же тему: совпадают ли
у них H1, title, ключевые сущности в заголовках.

Частые находки:
- **H1, захардкоженный в шаблоне**, переопределяет корректный заголовок из базы. Проверять
  не только админку, но и код темы: `grep -rn "<текст H1>" wp-content/themes/<тема>/`.
- **Страница методики/о подходе, названная как страница услуги** — тянет коммерческий
  интент на себя.
- **Статьи блога с тем же термином в заголовке**, особенно без собственного `title`
  (тогда он собирается из длинного H1).

Каждая страница должна занимать свой интент: услуга → заказ; статья → объяснение;
кейс → доказательство; методика → стандарт. Пересечения разводятся заголовками и title.

## Шаг 5. Привести заголовки к тому, как ищут люди

Проверяется по конкурентам, которых ИИ и поиск реально показывают:

```bash
for u in <URL конкурентов>; do
  curl -sS -m 15 -A "Mozilla/5.0 ... Chrome/128.0" "$u" | tr -d '\n' \
    | grep -oE "<title>[^<]*</title>|<meta name=\"description\" content=\"[^\"]*\"|<h1[^>]*>[^<]*</h1>"
done
```

Что обычно выясняется и что стоит перенять:
- H1 у всех — **прямое название услуги**, без креатива и слоганов.
- Title часто **дважды называет услугу разными формулировками** (ловит оба варианта
  запроса) и содержит регион и коммерческий сигнал («заказать»).
- Название сайта в title — через переменные SEO-плагина, не текстом.

Проверять, **как формулирует запрос клиент**, а не как принято внутри отрасли: термин
индустрии («GEO») и слово покупателя («продвижение в нейросетях») часто различаются, и
в заголовках нужны оба.

## Шаг 6. Убрать внутренний жаргон из первого экрана

Лид и блок метрик пишутся языком покупателя. Маркеры того, что текст написан для себя:
профессиональные термины («срез видимости», «промпты», «генеративные ответы»), названия
внутренних методик без расшифровки, метрики, смысл которых понятен только исполнителю.

Сверяться с другими страницами услуг того же сайта — обычно там уже есть рабочий паттерн
(глагол результата + конкретные условия), и профильная страница просто из него выпала.

## Шаг 7. Отправить на переобход и назначить контрольный замер

```bash
python scripts/yandex_webmaster_report.py --recrawl "<URL>"
```
**Google автоматизировать нечем:** Indexing API принимает только `JobPosting` и
`BroadcastEvent`, URL Inspection API умеет лишь читать статус. Переобход запрашивается
руками в Search Console по одному URL.

Контрольный замер — через 2–4 недели: повторить исходный запрос к ИИ дословно и
зафиксировать, какую страницу он называет теперь.

**Предупредить владельца заранее:** после удаления старого ранжирующегося URL показы по
теме просядут на несколько недель. Это ожидаемое следствие, а не поломка, и его лучше
проговорить до работ, а не объяснять после.

## Чего не делать

- **Не диагностировать и не «чинить» через `llms.txt`.** Стандарт не читает ни одна крупная
  ИИ-система (Google, OpenAI, Anthropic его не адаптировали; при замере Ahrefs на 137 тыс.
  доменов 97% файлов за месяц не получили ни одного запроса). Файл не может быть ни
  причиной, ни решением.
- **Не добавлять эмодзи в title/description ради CTR.** Google выводит их в title примерно
  в 0,012% выдач, вырезая в остальных; замеры противоречивы, есть зафиксированное падение
  трафика на 5%. Плюс проблема доступности: скринридеры зачитывают их вслух.
- **Не вылизывать meta description как основной рычаг.** Он не фактор ранжирования и
  переписывается поисковиком в 63–87% случаев подстановкой пассажа **из тела страницы** —
  значит работать надо с текстом страницы. Это тот же механизм, по которому ИИ выбирает
  цитату, так что рычаг общий.
- **Не чинить показанный экземпляр вместо причины.** Указали на одно поле/одну страницу —
  проверить, не системная ли это ошибка (в исходном разборе мусорное поле, показанное на
  одной странице, нашлось на 88).
- **Не восстанавливать «пропавшее» значение, не спросив.** Владелец может править сайт
  параллельно, а CMS при сохранении формы перезаписывает поля целиком.
