# Индекс видимости: чек-лист замера — все грабли сессии 2026-08-22

Собрано после одной сессии, за которую замер по загородному строительству переделывался
несколько раз: неверная методика (органическая выдача вместо ИИ-ответов), выдуманные
числа в черновиках, неверный регион выборки, придуманный набор промптов вместо карты
интентов, зависший прогон, ложные срабатывания в распознавании брендов. Цель файла —
следующий замер проходит по этому списку один раз, с первого раза, без повторения тех же
ошибок. Общая спецификация сервиса — `../geo/index/SPEC.md`, разбор архитектуры —
`../decisions/2026-08-22-indeks-vidimosti-format-i-masshtab.md`.

## Порядок действий по шагам (следовать по порядку, не пропускать)

### 0. Выбор отрасли и региона

- [ ] Отрасль соответствует золотому ICP: чек 2 000–50 000 BYN, высокая цена ошибки,
      покупатель реально спрашивает совета у ИИ перед выбором
      (`../expert/opinions/2026-08-21-geo-buyer-psychology-validation-high-ticket-icp.md`).
- [ ] **Регион замера = регион, который упоминают сами промпты.** Если промпты про «всю
      Беларусь» — выборка компаний тоже должна быть по всей Беларуси, не по одной области.
      Несовпадение регионов промптов и выборки — реальная ошибка, найденная и исправленная
      в этой сессии (выборка расширена с 232 компаний Минской области до 328 по стране).
- [ ] Источник выборки компаний — файл с брендом, сайтом, регионом (Excel из Яндекс.Карт
      или аналог). База ЕГР из CRM для этого не годится: там юридические названия
      («ООО "Ле Контабль"»), а нейросеть называет бренды, а не юрлица.

### 1. Карта интентов — ОБЯЗАТЕЛЬНО до формулировки промптов

**Грабля:** первый набор промптов был придуман из здравого смысла, без проверки по
Wordstat. Результат — половина промптов оказалась с околонулевой частотностью
(«кому доверить, чтобы не бросили объект» — 0 показов), а самый тяжёлый кластер спроса
(«каркасные дома», 43 688 показов/мес) отсутствовал вовсе.

- [ ] Собрать 10–15 сид-фраз по отрасли, прогнать каждую через Wordstat XMLRiver
      (`http://xmlriver.com/wordstat/new/json`, **параметр называется `regions`, не
      `region`** — без него уходит российская статистика вместо белорусской).
      Регион Беларуси — `regions=149`.
- [ ] Взять поле `popular` из ответа (не `associations` — это подсказки, не частотность
      самого запроса).
- [ ] Сгруппировать собранные запросы в 6–8 смысловых интентов по регуляркам (технология,
      цена, выбор подрядчика, география, проект, доверие/отзывы).
- [ ] Отсечь запросы с частотностью ниже ~50–100 показов/мес — они искажают картину.
- [ ] Под каждый ТЯЖЁЛЫЙ интент (не под каждый лёгкий) сформулировать один L0-промпт —
      разговорный вопрос, как его задают нейросети, а не короткую поисковую фразу
      (методика — `../geo/2026-08-16-mehanika-dekompozitsii-zaprosov.md`).
- [ ] Промпты для ценовых запросов — отдельная группа. В отраслях, где цена не фиксирована
      до проекта (стройка, ремонт, разработка), нейросеть на чистый ценовой вопрос не
      называет компаний вообще — отвечает диапазонами. Формулировка вида «сколько стоит
      X и кто это делает» (с добавлением «и кто это делает») переключает ответ в
      коммерческий режим и начинает называть компании — это не баг, а наблюдение, которое
      меняет результат сильно в зависимости от точной формулировки.
- [ ] **Технический баг, который стоит помнить:** список запросов хранится в
      `queries.md` со служебным комментарием вида `<!-- 43688 показов -->` — если парсер
      не вырезает `<!-- ... -->`, этот мусор уезжает в промпт вместе с вопросом и портит
      весь прогон. Проверено и починено в `scripts/index_measure.py::parse_queries`.

### 2. Движки и их особенности — прочитано из документации, не угадано

**Правило CLAUDE.md п.9, найденное на практике этой сессии:** перед работой с любым
внешним API — карта документации (`/sitemap.xml` или краулинг индекса), потом обязательно
разделы про коды ошибок, режимы и лимиты, и только потом код. 40 минут ушло на прогон,
который висел из-за того, что не была прочитана страница с таймаутами.

| Движок | Как получить ИИ-ответ | Особенности |
|---|---|---|
| **Google AI Overview** | XMLRiver, `http://xmlriver.com/search/xml?...&ai=1` | Формат ответа: `<ai><answer>base64</answer><item><title><url></item></ai>`. Отвечает стабильно, ~86% содержательных ответов на коммерческие запросы |
| **Яндекс / Обзор от Алисы** | XMLRiver, `http://xmlriver.com/search_yandex/xml?...&ai=1` | **Другой формат!** `<ai><item><content>base64</content><position><type></item></ai>` — код, который парсит только гугловский `<answer>`, не увидит ничего у Яндекса. Плюс: платная опция «Обзор от Алисы» должна быть включена в личном кабинете XMLRiver (25 руб/1000 + 10 наценка) — без неё приходит только `<present>1</present>` без текста. **Даёт содержательный ИИ-ответ лишь в ~30–43% случаев на коммерческие запросы** — это измеренный факт, не баг замера, отдельная ценная находка для публикации |
| **ChatGPT** | ProxyAPI (`api.proxyapi.ru`), `POST /openai/v1/responses`, `tools:[{"type":"web_search"}]` | Без `web_search` в `tools` модель отвечает из весов без поиска и не называет локальные бренды вообще — так и был испорчен старый baseline GAS. С поиском — ~100% содержательных ответов. Стоимость ~1 руб/поиск + токены, реально выходит ~2–3 руб за вызов — это **основная статья расходов**, XMLRiver на два порядка дешевле |

- [ ] Перед первым прогоном по новому движку — один тестовый запрос вручную, проверить
      формат ответа глазами, не полагаться на предположение «формат как у соседнего
      движка».
- [ ] XMLRiver документация по режимам: **синхронный режим отвечает максимум за 1 минуту**
      (обычно 3–6 сек), но при `ai=1` парсинг ИИ-блока может не укладываться в 10-секундный
      таймаут отдельных внутренних запросов — отсюда частые `error 500` («Выполните
      перезапрос»); **до 20% таких ошибок — документированная норма**, нужен повтор,
      а не диагноз «сервис лёг».
- [ ] **Стандартный аккаунт XMLRiver держит 10 параллельных потоков** (код ошибки 115 —
      это превышение лимита, а не сам факт параллельных запросов). Прогон в 90+ запросов
      последовательно с паузами занимает ~40 минут; тот же прогон с `ThreadPoolExecutor`
      на 8 потоках — единицы минут. Не гонять последовательно из перестраховки.

### 3. Распознавание брендов в тексте ответа — три источника ложных срабатываний, все найдены на практике

- [ ] **Общеотраслевые слова.** Название вроде «Деревянные дома» или «Строим Дом»
      совпадёт с обычной фразой в любом ответе про стройку («деревянные дома из бруса»,
      «мы строим каркасные дома»). Список стоп-слов (`GENERIC_WORDS` в `index_measure.py`)
      — названия, целиком составленные из таких слов, засчитываются только по совпадению
      домена сайта, не по тексту.
- [ ] **Отсутствие границ слова.** «Барнхаус» без `\b`-границ ловится внутри чужого
      названия «БарнХаусБел». Нужна проверка границ с обеих сторон, с допуском в 1–2 буквы
      на склонение (чтобы «Хата» ловило «Хаты», но не ловило «ХатаПлюс»).
      Правильная граница: `(?<![0-9a-zа-я])стем[а-я]{0,2}(?![0-9a-zа-я])`.
- [ ] **Дубли форм одного названия.** «Зодчий» и «Зодчие» — одна компания, но без
      канонизации считаются дважды. Функция `canon()` схлопывает окончания перед сравнением.
- [ ] **Круг компаний в ответах шире любой готовой выборки.** ИИ называет фирмы, которых
      нет в исходном Excel/базе (найдено на живых ответах: «Спектр» с 13 упоминаниями
      появился только после расширения региона). Топ строится **из того, кого ИИ реально
      называет** (`extract_brands()`), а не из пересечения ответа с готовым списком —
      иначе теряются настоящие лидеры.
- [ ] После каждого прогона — выборочно прочитать 3–5 сырых текстов ответов глазами и
      свериться со списком найденных совпадений. Автоматика один раз в этой сессии дала
      «8 брендов» из фразы Яндекса про способы поиска жилья («Рекомендации знакомых»,
      «Строительные выставки») — не про компании вообще.
- [ ] **Ручная сверка подтвердила методику, но вскрыла дыру в исходной базе.** Егор
      прогнал вручную три промпта из замера (2026-08-22) и сравнил с нашими данными:
      совпадения были там, где ожидалось (Белсруб, Вирабуд, Рувитстрой, Каркас Хаус,
      Каркасно-брусовые технологии, ТеремЪ подтвердились дословно). Но в его ручном
      ответе всплыли BlockHouse.by и Rkts-stroy — реальные конкуренты, которых **не было
      в исходном Excel-экспорте с Яндекс.Карт вообще**. Rkts-stroy наш `extract_brands()`
      всё же поймал из текста (не зависит от готовой базы), BlockHouse.by — нет, его
      просто не было ни в каком виде. **Вывод: после первого прогона отрасли — дополнить
      `companies.json` теми брендами, кого реально называют нейросети, но кого нет в
      исходной выборке** (`extract_brands()` + список источников `sources` — готовый
      источник кандидатов на добавление). Иначе конкурент реально видим для клиента, но
      невидим для нашего замера.

### 4. Стоп-правило: числа только из завершённого замера

**Самая серьёзная ошибка сессии.** Параллельная сессия опубликовала 14 черновиков
страниц с числами вида «7 из 15», взятыми из **пробного прогона на одном запросе**; одна
компания попала в топ-3, вообще не участвуя в замере — её домен был просто в списке
источников. Это не ошибка метода (как утром с GAS), а публикация выдуманных данных о
реальных сторонних компаниях под именем FastUp.

- [ ] Перед подстановкой любого числа на страницу — проверить сам файл `*-data.json`:
      `queries` содержит полный список (не 1-2), `engines` — все заявленные движки,
      `runs` соответствует заявленному, `hits` не пустой.
- [ ] Файлы с суффиксом `-probe`/`-speedtest` — только для проверки формата ответа,
      никогда не источник чисел для публикации. Удалять после того как убедились, что
      формат рабочий, не путать с финальным файлом при последующей генерации страниц.
- [ ] `scripts/index_build_page.py` и промпт `geo/index/PROMPT-stranitsa.md` уже содержат
      эту проверку встроенной (`validate()` отказывает генерировать страницу из
      некомплектных данных) — использовать эти инструменты, не писать вручную заново.

### 5. Инкрементальная запись результата

`scripts/index_measure.py` пишет `*-data.json` **после каждого ответа**, не только в
конце. Если это когда-то будет переписано заново — обязательно сохранить это свойство:
без него часовой прогон, прерванный на 55-й минуте, теряется целиком.

## Стоимость одного полного прогона (ориентир)

- XMLRiver (Google + Яндекс, `ai=1`): ~35 руб/1000 запросов — copейки на весь замер.
- ProxyAPI (ChatGPT, `web_search`): ~2–3 руб за вызов — при 15 промптах × 3 прогона это
  ~100–150 руб. **Это основная статья расходов**, XMLRiver в сравнении бесплатен.
- Итог на одну отрасль, 3 прогона, 3 движка: порядка 150–200 руб.

## Что проверять, но НЕ переделывать (уже закрыто)

- Регулярка `mentioned()` и `extract_brands()` в `scripts/index_measure.py` — рабочая
  версия после всех правок, дополнительно перепроверена на реальных данных
  загородного строительства.
- Формат хранения `geo/index/<отрасль>/{companies.json, queries.md, <год-месяц>-data.json}`
  и общий реестр `geo/index/industries.json` — не менять структуру без крайней нужды,
  под неё уже написаны оба шаблона темы.
